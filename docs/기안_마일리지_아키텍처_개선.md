- 작성일: 2026-04-26

## 1. 현재 상황 및 문제

### 증상
리더보드에 표시되는 마일리지(예: 80점)와 멤버 카드를 눌렀을 때 나오는 상세 합산(예: 90점)이 일치하지 않는다.

### 근본 원인 구조

현재 마일리지는 **두 군데에서 따로 계산**된다.

```
[리더보드]
club_workout_mileage 테이블 (스냅샷)
→ 운동 저장 시점에 앱 코드가 계산해서 DB에 써둔 값

[멤버 상세 모달]
workouts 테이블 → 현재 계수로 실시간 계산
```

이 두 소스가 다르기 때문에 값이 달라진다.

### 스냅샷이 틀어지는 경로

#### 경로 1 — saveWorkoutMileage 실패
운동 저장 시 앱이 각 클럽에 마일리지를 저장하는데, 실패하면 조용히 넘어간다.

```
운동 저장 성공
  └─ saveWorkoutMileage() 호출
       └─ 실패 → catch → console.error → 끝 (스냅샷 누락)
```

실제로 April 24, 25일 운동 2건이 이 경로로 누락 확인됨.

#### 경로 2 — Promise.all 연쇄 실패
클럽이 여러 개일 때, 하나 실패하면 나머지 클럽도 전부 실패한다.

```
Promise.all([클럽A 저장, 클럽B 저장, 클럽C 저장])
→ 클럽B 실패 → 전체 throw → A, C도 누락
```

#### 경로 3 — 계수가 JSON 컬럼에 저장됨
현재 구조:
```
clubs.mileage_config = {
  "달리기-러닝": 1,
  "사이클-실외": 3,
  ...
}
clubs.enabled_categories = ["달리기-러닝", "달리기-트레드밀"]
```

- 앱 코드가 이 JSON을 읽어 계수를 적용
- DB는 이 계수를 전혀 모름 → DB 수준의 자동화 불가
- 계수 변경 시 기존 스냅샷과 불일치 발생

---

## 2. 개선 목표

1. 리더보드와 상세 모달의 마일리지가 **항상 일치**한다
2. 운동 저장/수정/삭제 시 스냅샷이 **자동으로** 정확하게 반영된다
3. 앱 코드(JavaScript)가 DB 동기화 책임을 지지 않는다

## 3. 변경 내용

### 3-1. 계수 테이블 신설 (club_mileage_configs)

**현재**
```sql
-- clubs 테이블 컬럼
mileage_config     jsonb   -- {"달리기-러닝": 1, "사이클-실외": 3}
enabled_categories jsonb   -- ["달리기-러닝", "달리기-트레드밀"]
```

**변경 후**
```sql
CREATE TABLE club_mileage_configs (
  club_id     uuid    REFERENCES clubs(id) ON DELETE CASCADE,
  category    text    NOT NULL,   -- 예: '달리기'
  sub_type    text,               -- 예: '러닝', 없으면 NULL
  coefficient numeric NOT NULL DEFAULT 1,
  enabled     boolean NOT NULL DEFAULT true,
  PRIMARY KEY (club_id, category, COALESCE(sub_type, ''))
);
```

| 컬럼 | 설명 | 예시 |
|------|------|------|
| club_id | 어느 클럽의 설정인지 | (uuid) |
| category | 운동 대분류 | 달리기, 사이클 |
| sub_type | 운동 소분류 (없으면 NULL) | 러닝, 트레드밀 |
| coefficient | 계수 (값 ÷ 계수 = 마일리지) | 1, 3, 5 |
| enabled | 이 운동 종목을 마일리지에 포함할지 | true/false |

기존 `clubs.mileage_config`와 `clubs.enabled_categories` 컬럼은 **마이그레이션 후 삭제**.

---

### 3-2. DB 트리거 신설

`workouts` 테이블에 운동이 추가/수정/삭제될 때, **DB가 직접** 마일리지를 계산해서 `club_workout_mileage`를 갱신한다.

```
[운동 저장/수정/삭제]
        ↓
  workouts 테이블 변경
        ↓
  DB 트리거 자동 실행
  ┌────────────────────────────────────────┐
  │ 1. 이 유저가 속한 클럽 조회            │
  │    (club_members)                      │
  │ 2. 각 클럽의 계수 조회                 │
  │    (club_mileage_configs)              │
  │ 3. 마일리지 계산                       │
  │    value ÷ coefficient = mileage       │
  │ 4. club_workout_mileage UPSERT         │
  └────────────────────────────────────────┘
        ↓
  리더보드 조회 시 항상 정확한 값
```

트리거가 DB 내부에서 실행되므로:
- 앱 코드 성공/실패와 **무관하게** 항상 동기화
- 네트워크 오류, 앱 크래시 등 외부 요인 영향 없음

---

### 3-3. 현재 월 랭킹 조회 방식 변경

**현재**: `club_workout_mileage` 스냅샷 읽기 (앱 동기화 의존)

**변경 후**: 트리거가 항상 최신 상태로 유지하므로 `club_workout_mileage` 조회 동일하게 유지. 단, 리더보드와 모달이 **같은 데이터 소스**를 보게 됨.

모달도 `club_workout_mileage`에서 읽도록 변경:
```
[리더보드]  club_workout_mileage 조회
[모달]      club_workout_mileage 조회 (현재: workouts 직접 계산 → 변경)
```

→ 두 화면이 **동일한 테이블**을 보므로 불일치 원천 차단.

---

### 3-4. 지난달 스냅샷 처리

월이 바뀌는 시점에 해당 월의 `club_workout_mileage` 데이터를 그대로 유지한다. 트리거는 `workout_time` 기준 KST 날짜로 year/month를 기록하므로, 지난달 데이터는 자연스럽게 고정된다.

## 4. 마이그레이션 계획

### Step 1. 테이블 생성
```sql
-- club_mileage_configs 테이블 생성
```

### Step 2. 기존 데이터 이전
```sql
-- clubs.mileage_config JSON → club_mileage_configs 행으로 변환
-- clubs.enabled_categories JSON → enabled 컬럼으로 변환
```

### Step 3. 트리거 작성 및 적용
```sql
-- workouts INSERT/UPDATE/DELETE 트리거
```

### Step 4. 앱 코드 수정
- `clubService.saveWorkoutMileage()` 호출 제거
- `clubService.getClubRanking()` — 스냅샷 count 체크 로직 제거 (트리거가 보장)
- `ClubMemberDetailModal` — workouts 직접 계산 → `club_workout_mileage` 조회로 변경
- `ClubMileageSettings` — `club_mileage_configs` 테이블 읽기/쓰기로 변경

### Step 5. 구버전 컬럼 삭제
```sql
ALTER TABLE clubs DROP COLUMN mileage_config;
ALTER TABLE clubs DROP COLUMN enabled_categories;
```

## 6. 기대 효과

- **리더보드 ↔ 모달 불일치 문제**: 완전 해결
- **스냅샷 누락 문제**: 원천 차단 (DB 트리거 보장)
- **마일리지 재계산 버튼**: 계수 변경 시에만 필요 (현재와 동일)
- **코드 복잡도**: 감소 (saveWorkoutMileage 관련 코드 전부 제거)
